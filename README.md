# Scout — Shopify Lead Intelligence

An agency research workspace for discovering Shopify stores, collecting public audit evidence, reviewing prospect eligibility, and generating private PDF reports.

**Implementation status:** runnable MVP with real provider adapters and a persistent Supabase job queue. A labeled synthetic demo is available without credentials. A small manual test has verified live Tavily discovery, PageSpeed auditing, Supabase persistence, and private PDF storage. The database is also regression-tested with embedded PostgreSQL. Other discovery providers, optional browser/AI/history modules, and deployed operation still need live verification.

## Run the application

Requires Node 20.19+ (Node 22 recommended for new deployments).

```sh
npm ci
cp .env.example .env
npm run dev
```

Open [localhost:5173](http://localhost:5173). With no credentials, Scout opens its demo workspace. Sample businesses use reserved `.example` domains. Demo edits stay in browser storage. Discovery and re-audit controls explain the required live configuration rather than simulating work. Demo CSV/PDF exports explicitly identify synthetic data.

## Enable live research

1. Create a Supabase project. In the Supabase SQL editor, apply **all migrations in filename order** from `supabase/migrations/`. Alternatively, link the project using the Supabase CLI and run `supabase db push`. The migrations create the normalized tables, RLS policies, service-only queue RPCs, and private `audit-artifacts` bucket. Never run these against an unrelated existing schema.
2. Enable Supabase email/password authentication. Set your application URL and allowed redirect URLs in the Supabase Auth configuration. Email confirmation follows your project policy; arrange SMTP delivery for production. Set a secure password policy in Supabase.
3. Fill `.env` with the project URL, public publishable key (`sb_publishable_...`), and server-only secret key (`sb_secret_...`). Both `VITE_SUPABASE_URL` and `SUPABASE_URL` must refer to the same project. Only the publishable key and public URL are exposed in the frontend.
4. Run `npm run check:connections` to verify public authentication, server database access and the private report bucket without creating jobs or calling paid providers. Then add a Google PageSpeed API key and **one** discovery provider key (Store Leads, Brave Search, or Tavily). Optional modules require the dependencies listed below.
5. Restart the dev server. Choose **Connect your workspace**, create an account/sign in, and create your agency workspace. Configure discovery criteria, thresholds, budget, and optional modules. The creating user is a workspace owner. Member invitations/role administration are not included in this MVP; provision additional members through a trusted administrative workflow.
6. In a separate terminal, start the persistent worker:

```sh
npm run worker
```

For a setup pause, start `WORKER_PAUSED=true npm run worker`. The worker verifies its database connection but does not claim jobs or run retention cleanup. Restart it with `npm run worker` after the required credentials are ready. On macOS, `npm run mac:worker -- install` adds automatic login startup and crash recovery; see [Mac worker setup](docs/MAC_WORKER.md). The Mac must remain logged in, awake and online. A later server move is documented in [worker deployment](docs/WORKER_DEPLOYMENT.md).

7. Save a discovery configuration and select **New discovery → Run discovery**. Watch **Automation Jobs**. Leave scheduling enabled for recurring runs. The worker must stay running for scheduled work; logging into the dashboard is not required.

Use **Stop discovery** on Store Discovery, Settings, or Automation Jobs to cancel queued/running discovery and disable all discovery schedules in the workspace. Audits already queued continue; use **Cancel job** on an individual queued/running audit or discovery job to stop it. Cancelling one job leaves its schedule unchanged. Completed findings and reports are kept. A provider request already sent may finish and count toward usage; cancellation prevents further work at the next checkpoint. These controls require migration `004_job_cancellation.sql` and the updated worker. Restart existing workers after updating the code; keep `WORKER_PAUSED=true` while credentials are being configured.

They are shared per organization per UTC date; the limit configured for the running discovery query is used for each reservation. Select a budget that covers discovery plus at least six PageSpeed requests per qualified store.

[Search API reference](https://docs.tavily.com/documentation/api-reference/endpoint/search). Never place this key in a `VITE_` variable or in browser storage.

Supabase now recommends publishable and secret keys ([official key guide](https://supabase.com/docs/guides/getting-started/api-keys)). Legacy environment names remain supported for existing configurations. Put credentials in the ignored local `.env`; do not paste secret keys into chat. Workspace creation explicitly uses the public key with the signed-in user token.

## Implemented workflow

- Supabase signup/sign-in, organization membership and tenant isolation.
- Scheduled/manual discovery, canonical-domain deduplication, evidence-based Shopify checks, public activity confidence, country provenance and automatic audit enqueueing. Country evidence accepts same-business JSON-LD or explicit public business addresses with a named country, street and postal pattern; shipping markets and ambiguous offices do not establish country.
- Discovery skips stores with any retained audit or audit job in the workspace, including domains that redirect to a known store. This full-history check is independent of Tavily's most recent 100 excluded domains and saved search criteria. Stores saved before a crash but never queued remain recoverable. Explicit manual re-audits still work; normal retention removes old research according to the saved policy.
- Mobile/desktop PSI screening, any-condition qualification, individual diagnostics and field-data scope, and three-sample medians on shortlisted homepages. Absent CrUX data is unavailable; lab TBT is never treated as INP.
- Bounded representative homepage, collection, product, contact and about HTML inspection. Missing titles/descriptions/H1, duplicate titles, noindex signals, invalid JSON-LD, image alt/dimension attributes, duplicate script references and detectable marketing-script evidence.
- Optional read-only mobile screenshots, browser console/resource observations, rendered image dimensions, and horizontal overflow detection. Browser failures and blocked requests are retained as diagnostic context.
- Optional historical availability lookup and evidence-referenced AI recommendations.
- A 100-point research score with one piece of evidence behind each part, shown on each lead: ideal-client fit, verified opportunity, timing, store activity, contact route and scope. Timing comes only from observed changes (new products, catalog growth, a mobile score drop, a newly added tool) and never implies buying intent. Priority stays 0 until the country, Shopify and outreach review checks pass.
- Won/lost outcomes on each lead, which feed search learning.
- Separate technical opportunity strength (Strong / Moderate / Needs evidence) and outreach review status. Strong requires a supported high-severity finding or mobile performance below 50 with a verified finding; it does not infer buying intent. The older gated outreach-priority model remains available for approved prospects. Suppression and permission gates remain mandatory.
- Lead search, country/stage/priority filters, sorting, selection, pagination, CSV export, notes/owner/stage, audit history, manual re-audit, private PDF downloads, and human contact-eligibility review with rationale and 30-day expiry. **There is no outreach-sending integration.**
- Public email extraction from explicit mailto links and same-domain page text, with source URLs in lead details and CSV exports. Missing addresses stay unknown; each domain is checked for a mail server, but mailboxes aren't confirmed. Refresh contacts for existing leads without another PageSpeed audit using `npm run refresh:contacts -- <organization UUID>`.
- Readable private PDF audits include an executive summary, mobile/desktop score and metric medians, separate real-user data, grouped findings with linked examples, an action plan with acceptance checks, public contact details, audit scope and evidence references. Cached results and missing measurements are disclosed. Legacy downloads upgrade from saved evidence without provider calls. Preview retained reports with `npm run refresh:reports -- <organization UUID>`; add `--publish` to update their private downloads, optionally selecting `--report=<report UUID>`. Original PDF objects are preserved.
- A moderate screening preset selects up to 10 stores per run with mobile performance ≤75 or SEO ≤85. Supported frontend/image/accessibility findings can also qualify when enabled; numeric modernization heuristics are no longer presented or generated. Any one observed condition can qualify; platform, country, and activity verification remain mandatory. Tavily checks up to 60 search results with the three-search setting, so the selected count and final lead count may still be smaller. Automation Jobs shows raw results, parsed candidates, Shopify/activity/country checks, suppressed/previously researched counts, and queued audits, plus each query and its filtering counts.
- Queue IDs, leases/heartbeats, attempts, exponential retry delay, progress, errors and provider usage. A partial unique index prevents duplicate active audit jobs. Final publication checks current lease ownership and suppression in a database transaction.
- Configurable retention (30–3,650 days via API; common intervals in UI). Hourly worker cleanup handles up to 25 expired stores per organization per pass and removes private artifacts before cascading research deletion. Suppression records remain. Opt-outs are applied from the lead review screen and block future audit/approval.

The main **Leads** view and command search query the full retained workspace history with database filtering and pagination (10/20/50 per page). Filtered exports traverse those database pages, with an explicit 5,000-lead export limit; narrow filters for larger exports. Other overview/secondary views still use the newest **500 leads** and newest **100 jobs** snapshot window. No claim of exhaustive search-engine discovery is made.

## Lead and discovery workflow

Apply migrations through `010_lead_outcomes.sql`. Use `npm run refresh:scores -- <organization UUID>` to recalculate saved research scores from retained evidence, which the Leads sort reads; add `--dry-run` to preview without saving. Its only lookups are free DNS checks of each email domain, which show whether the domain has a mail server; they can't confirm a mailbox exists, and a failed lookup stays unknown. Use `npm run refresh:intelligence -- <organization UUID>` to infer industries and shorten names from retained audit evidence; this makes no provider requests, preserves original titles and manual industry corrections, and initializes category budgets without raising the total cap.

The Leads table shows the main supported opportunity, contact category, review state and next action. Open a lead for a three-part brief (why this store, a scoped service, next step), editable business name/industry, preferred published email, source evidence and notes. Contact categories are routing hints based on the address, not verified employment roles or deliverability. Careers and wholesale addresses are ranked below general/support contacts; an explicit preferred address wins. Saved lead views are scoped to the workspace in this browser and survive reloads.

Client-readable findings group repeated observations, explain recommended fixes and validation, and keep raw evidence in nested disclosures. Contrast examples use recorded values only. Hypotheses stay separate. No paid LLM summarization is needed.

Create separate focused campaigns on Store Discovery or Settings; presets narrow country and industry without enabling schedules. Tavily retains basic depth and the existing per-run search cap. New runs record individual query outcomes and the originating search for each child audit. Adaptive rotation skips a keyword/country/industry combination temporarily after two recorded completed searches yielded no new audits; custom domain exclusions remove recurring irrelevant sources. Search analytics disclose their recent-data window; historical searches without individual attribution are not assigned invented outcomes.

Active Shopify stores with unverified countries enter a pending review queue. An administrator can record a supported country and public evidence, then queue an audit. Import known stores via domain lists or CSV (up to 50 at a time); preview skips duplicates, prior research and suppressed domains before enqueueing. Imports use no discovery search credits, while qualifying audits still use provider requests. First-audit imports are idempotent across completed jobs; manual re-audit remains available separately.

The Jobs and Settings screens show worker heartbeat status and daily discovery/audit request counts. Separate category limits and the shared total apply workspace-wide and reset at midnight UTC. Budget-blocked jobs wait until the next UTC day without exhausting attempts. For an existing always-on server, see [worker deployment](docs/WORKER_DEPLOYMENT.md) and `compose.worker.yaml`; a prepared deployment configuration is not evidence of a deployed worker.

## Automation Jobs

The page leads with one status line (what Scout is doing and what to do next), then anything that needs attention, what's running with a live map, today's numbers, all jobs, and schedules. Each job has its own page at `/jobs/<id>` with the full map, activity and evidence; `/jobs/sample` plays a fictional run that starts no work. While a job runs, a small S.C.O.U.T. core sits in the corner of every other page and opens that job.

## Alerts and daily digest

The bell in the top bar lists problems first (worker offline, provider paused, budget reached, failed or blocked jobs), then new leads and outreach waiting for review, with a summary of the last 24 hours. To also get them outside the app, set `ALERT_WEBHOOK_URL` to a Slack or Discord incoming webhook and restart the worker and API. The worker checks every five minutes, sends each problem once a day, and sends one digest a day after `ALERT_DIGEST_HOUR_UTC`. A stopped worker can't report itself, so the API sends that alert, and only while the API is running. Sent alerts are remembered in `SCOUT_ALERT_STATE_DIR` (default `/tmp`).

## Evidence scope and further work

The larger product brief includes deeper features than this MVP implements. These remain explicit follow-up work:

- Historical screenshot retrieval, rendering and visual comparison over 12/24/36/60 months.
- Full multi-page performance sampling, redirect-chain reporting, XML sitemap parsing, broken-link crawling, complete heading/schema validation and comprehensive accessibility testing.
- Detailed image compression/savings analysis beyond available Lighthouse diagnostics and browser-observed metadata.
- Full visual CRO journey analysis and cart/variant interaction verification. Current product-control checks are HTML hypotheses, not verified purchase-flow defects. CRO scores are unknown in live research until a supported assessment exists.
- Verified recent social/review/launch timing signals and richer public business-category/contact-role research.
- Private CRM flows, analytics, sales, conversion rates, Shopify theme source/version and Google index coverage cannot be established by unauthenticated public inspection. These are **unknown**, not silently inferred.
- Production operational additions: member invitations, key rotation workflow, deployment monitoring/alerts, distributed per-domain crawling limits across many worker replicas, and a production load/penetration review.

Network access blocks nonpublic/reserved IP ranges, pins validated DNS, validates redirects, follows robots rules, imposes response/time/page caps, and never submits forms/orders or bypasses authentication. Start with **one worker replica** to keep per-target pacing predictable. Do not enable aggressive multi-worker crawling without distributed per-domain limits.

## Production deployment

The frontend and API deploy as one Node web service; the worker deploys as a **separate always-on process** against the same Supabase project. Use an HTTPS reverse proxy and configure `APP_ORIGIN` to the exact public origin. If a proxy supplies client IPs, configure Express trust-proxy deliberately for that platform; it is off by default.

```sh
npm ci
npm run build
npm start
# separate service with the same server environment:
npm run worker
```

`npm start` serves `dist/` and `/api` on `PORT` (default 3001). The worker is not a short-lived serverless request. Use the included Dockerfile and compose example, or create web/worker services on a persistent container host. Do not deploy the worker into a static-only host. The basic container supports the MVP; build the optional `browser-worker` target for Chromium diagnostics.

Vite public variables are embedded **at build time**. Set `VITE_ENABLE_DEMO=false` in both build and server environments to disable the synthetic preview in production. Do not set any server secret with a `VITE_` prefix. Exclude `.env` and local artifacts from deployment source. Database migrations run once before starting services and are not automatically executed by the container.
